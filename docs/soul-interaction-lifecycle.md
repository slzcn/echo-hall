# 灵魂交互消息生命周期契约

- 日期：2026-08-14
- 触发事件：灵魂发起成语接龙/小游戏/邀请等可交互消息后，用户过一会儿才来接，灵魂上下文已滚出窗口，接续没人应，形成"钓鱼死链"体验差。
- 责任人：小龙虾（自动化实现 + 测试）

## 契约动机

灵魂 tick 只看最近 16 条房间消息做上下文（`supabase/functions/eh-soul-tick/index.ts` 的 `recentMessages(rid, limit=16)`）。灵魂发起的可交互消息只要被后续 ≥16 条消息冲掉，灵魂 tick 再也看不见它，用户接续时得不到回应。这是隐性 UX 契约，必须显式化。

## 生命周期定义

当前仓库事实：`kind='interact'` 是送花、抱抱、攻击等即时特效，不是成语接龙；`kind='game'` 目前只有海龟汤和斗地主，尚无成语接龙协议。因此本契约先定义未来“带生命周期元数据的灵魂小游戏”应具备的三态，**不对现有 interact 或普通 msg 误套过期逻辑**。未来协议建议使用 `kind='game'` + `game_type` + `game_id` + `expires_at` + `status`，且 `is_bot=true` 才进入本契约：

| 态 | 判定 | 呈现 | 交互 |
|---|---|---|---|
| 活跃 active | 未触发任何过期条件 | 正常渲染 | 正常点击/回应 |
| 过期 expired | 触发任一过期条件 | 置灰 opacity 0.5 + 底部小字"这段互动灵魂已经不记得了~" | 点击/回应按钮无响应；已回应过的历史消息保持可见 |
| 已完成 done | 用户已回应且被灵魂 ack 过 | 正常样式，不变过期态 | 无新交互 |

**始终不删除消息**，因为消息流的完整性是 Echo 的核心体验。

## 过期条件（任一命中即过期）

1. **时长阈值**：发起时刻距今 > `SOUL_INTERACT_TTL_MS = 10 * 60 * 1000`（10 分钟）；
2. **窗口滚出**：发起消息之后同房间已有 ≥16 条 `kind in (msg,act,voice,song)` 消息（与灵魂 tick 的 `limit=16` 对齐）；
3. **灵魂离线**：发起灵魂当前不在房间在线名单里（`roomSouls` 无此灵魂或该灵魂 `enabled=false`）；
4. **房间已空**：房间目前无真人在线（`humansOnlineCount === 0`）。

命中任一即"过期"。前端渲染层**独立判定**，不依赖后端；后端只在灵魂 tick 时**跳过已过期的孤儿邀请**（不再对超窗消息生成兜底应答，避免"过期后突然复活"）。

## 呈现细则

- 过期态卡片样式：`.eh-interact-card.expired { opacity: .5; filter: grayscale(.4); }`
- 过期文案挂在卡片底部：`<span class="eh-interact-expired-hint">这段互动灵魂已经不记得了~</span>`
- 可点击控件（按钮/输入框）加 `pointer-events: none` 或 `disabled`
- 用户已经在过期之前接续过的历史消息**保持原样**，不追溯变灰

## 兜底措施

即使过期渲染逻辑失败，也要有以下保底：

1. **健康巡检**：`scripts/health-probe.py` 每日扫最近 24h 内 `kind='interact'` 且 `interactor='soul'` 且未被真人回应且已滚出窗口的消息，若数量 > 阈值报警到主人 IM
2. **灵魂 tick 兜底**：`eh-soul-tick` 拉最近 16 条前，先判断"最老那条 interact 是否已距离过久"，若已过期，可选补一句轻挽尊（"刚才走神了，我们随便聊聊"），避免用户面对纯沉默

## 反例（明确不做的）

- ❌ 不做"淡出/删除消息"——破坏消息流完整性
- ❌ 不做"强制灵魂无限延长上下文"——LLM token 成本失控
- ❌ 不做"用户点击过期卡片时弹重开对话框"——过期就是过期，不留悬念
- ❌ 不改数据库 schema——用现有字段和时间戳即可判定

## 当前实现边界（诚实验收）

- 已落地：契约文档、时间轴测试和旧实现反证。
