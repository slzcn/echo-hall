# 断联后刷新慢、偶发二次刷新

## §1 现象（Reproducibility）

- **设备**：用户反馈，具体机型未提供
- **OS 版本**：未提供
- **运行环境**：PWA／浏览器断联后恢复场景，具体浏览器未提供
- **主题/时段**：不限定
- **触发步骤**：
  1. 页面处于断联或弱网状态
  2. 恢复网络后刷新页面，或执行下拉刷新
  3. 观察页面加载与刷新次数
- **预期结果**：缓存壳应快速可用；一次刷新完成，不因 Service Worker 接管或版本检查再次刷新。
- **实际结果**：刷新等待时间较长，偶尔出现二次刷新。
- **修前视频/GIF**：未提供；本次先用代码路径、门禁和线上资源验证。

## §2 稳定复现

- 用户侧已报告稳定体验问题；本地未具备对应真机断联录屏条件。
- 代码审查确认三套刷新入口存在叠加路径：版本自愈、Service Worker controllerchange、下拉刷新。
- 本次验证以静态门禁、脚本语法、缓存策略检查和线上部署复测为主；真机多环境矩阵保留为上线后观察项。

## §3 单一根因假设

- **本次假设根因**：刷新链路的多个入口在弱网下等待网络，且 Service Worker 接管后无条件触发整页 reload，导致等待时间增加并可能重复刷新。
- **证据链**：
  1. 下拉刷新版本检查原有 2.5 秒超时。
  2. 页面版本自愈初始检查无超时，可能长期等待弱网请求。
  3. `controllerchange` 原有逻辑无条件 `location.reload()`，可与 hard reload／版本自愈的 `location.replace()` 叠加。
  4. 导航请求原有网络优先策略最长等待 3 秒才返回缓存壳。
- **可以证伪它的实验**：在 DevTools 将 `ver.txt`、导航请求和 SW 更新请求延迟或阻断，分别观察取消 controllerchange reload、缩短超时和缩短导航兜底时间是否消除重复刷新与长等待。
- **证伪结果**：未被证伪，继续修复。

## §4 修复方案

- **动到的文件**：`index.html`、`js/pull-refresh.js`、`js/sw-register.js`、`sw.js`、`ver.txt`、刷新相关门禁测试。
- **方案**：版本检查增加 800ms 超时并延后到 load 后 300ms；下拉刷新版本检查由 2.5s 降至 800ms；`controllerchange` 改为静默记录、不再无条件 reload；导航缓存兜底由 3s 降至 1.5s；统一刷新版本指纹。
- **是否影响其他平台**：影响所有使用 PWA／Service Worker 的浏览器；保留网络成功优先和离线缓存兜底，不改变业务数据刷新逻辑。
- **回滚方案**：回滚本原子提交即可恢复旧刷新策略，不涉及数据库或不可逆数据操作。
