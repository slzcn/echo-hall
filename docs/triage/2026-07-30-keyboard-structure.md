# Echo 键盘协同结构重构诊断单

## §1 现象

- 现象：聊天输入框与系统键盘协同问题仍存在；从不同场景进入房间时表现不一致。
- 已知路径：房间页直接刷新相对正常，从首页进入房间容易出现显示不全或输入区位置异常。
- 代码现状：`js/keyboard.js` 有两个独立 IIFE，分别处理聊天输入框与弹窗输入框；`.stage` 同时受 CSS、CSS 变量、内联样式和场景切换钩子控制。

## §2 稳定复现

- 真机型号与系统版本：待主人补充，本次先做结构性收敛，不宣称已完成真机验证。
- 桌面环境不能等价复现移动端系统键盘，不能作为真机结论。

## §3 单一根因假设

- 根因假设：键盘布局存在多个控制器和多个状态源，聊天输入框与弹窗输入框分别修改同一布局层，导致场景切换和键盘事件之间出现残留样式与时序竞争。
- 证据：
  1. `keyboard.js` 有两个键盘 IIFE。
  2. 聊天路径写 `--vh`、`data-kb-jsfallback`、`kb-up`，弹窗路径写 `.stage` 的 `transform`、`transition`、`data-kb-offset`。
  3. `goScene('hall')` 需要额外调用清理钩子，并重复调用两次。
- 证伪实验：保留 CSS 规则不变，仅将 JS 收敛为一个控制器，并移除所有历史内联样式清理分支；若多路径仍出现同样异常，再开新的诊断单分析具体设备的视口数值。

## §4 修复方案

- 文件：`js/keyboard.js`。
- 方案：一个 IIFE、一个视觉视口更新函数、一个恢复函数、一个弹窗输入滚动函数；不再启用 `VirtualKeyboard.overlaysContent`，不再维护 `kb-up`、`data-kb-offset` 和运行时诊断浮层。
- 回滚：回滚本次单文件 commit。
- 影响：iOS Safari/PWA、Android Chrome/PWA 的键盘布局；桌面无键盘路径保持 CSS 默认布局。
